1  What the module is

Profile is the single page where an associate sees everything the company records about them, and the only place they can correct their own personal details. It is deliberately read-mostly: employment facts such as hire date, employment status and reporting line are owned by HR and shown here without an edit control.

Who sees it. Every role. view profile is granted to Super Admin, Admin, HR, Manager, Team Lead and Employee alike, so Profile is the one module no role is ever without.

3  Where each field comes from

Profile is a join across five tables, not one. That matters when a field looks blank: the row may simply not exist yet for that user.

This is derived, not stored. ProfileResource reads the employee's employment_status and reports:

Keep these in step. The same rule is applied independently by LeaveCreditSeeder when it grants the year's credits. Change one and the other has to follow, or the label will contradict the credits on Leave Requests.

4  Editing your profile

Edit Profile opens a modal over the page. Only the personal and emergency contact blocks are editable; employment fields are rendered but disabled. Saving issues a single PUT /api/user/profile, and the page re-reads itself from the response rather than patching state locally, so what you see after saving is what the server stored.

  • Validation is server-side; field errors come back as a 422 and are shown inline.
  • There is no approval step — a personal detail change is live immediately.
  • Changing employment facts is HR's job, through User Management and Employee Regularization, not here.

6  API reference

VerbPathPermission
GET/api/user/profileview profile
PUT/api/user/profileedit profile
GET/api/user/profile/associate-logs/download/{log}view profile

The third route lets an associate download a document HR filed against them under Associate Logs — it is scoped to the signed-in user, so one associate cannot reach another's file by guessing an ID.
